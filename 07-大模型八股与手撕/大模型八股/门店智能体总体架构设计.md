# 门店智能体架构设计原则

基于当前 LLM 的能力边界，门店智能体场景短期内仍难以直接实现“一次性输入全量信息，并精准输出完整答案”的理想化模式。因此，在门店智能体的实际设计中，考虑到 LLM 在处理“大而全”的综合任务时，性能和效率难以兼顾，我们将复杂任务拆分为多个可独立处理的“小任务”，并采用模块化架构按步骤完成，从而提升回复质量、缩短响应延迟、降低生成成本。

## 架构核心特性

为满足智能体场景对响应时间（RT）的高要求，**每轮交互中的模型调用严格控制在两次以内**：

### 1. 第一次调用：意图识别
- 基于统一抽象的业务场景，精准识别用户意图。
- 将用户请求路由至对应的业务场景模块。
- 采用qwen-plus模型，基于prompt提示词，让大模型直接进行意图识别

### 2. 第二次调用：回复内容生成
- 在该阶段，LLM 融合多源数据生成最终响应，包括：
  - 业务 API 返回的实时信息  
  - RAG 检索到的商家知识与用户评论  
  - 用户画像等个性化数据
- 每个业务场景采用**独立子工作流**生成响应内容。
- 支持多种典型场景（如团购、订座/排队、到店礼、菜品推荐等），各场景拥有专属子工作流，确保：
  - 高可维护性  
  - 良好的扩展性  
  - 强化的场景化适配能力
 

## 核心设计原则

门店智能体架构采用 **“单 Agent 模式”**，整体方案可概括为：

> **业务场景统一抽象 + 分而治之 + 模块化子工作流 + 动态提示词**

该设计在保证模块化与多行业适配能力的同时，兼顾响应质量、交互效率与生成成本控制。

## 关键组件说明

### 1. 业务场景统一抽象
- 从行业特性及业务需求出发，对门店智能体的服务范围进行统一抽象与分类。
- 提炼出核心业务场景，例如：
  - 团购  
  - 订座 / 排队  
  - 到店礼  
  - 菜品推荐  
  - ……

### 2. 意图识别节点（第一次 LLM 调用）
- 基于上述统一抽象的业务场景分类，构建智能体的业务服务能力边界。
- 精准识别用户意图，并完成路由规划，将用户请求匹配至最合适的业务场景。

### 3. 业务场景子工作流 Agent（第二次 LLM 调用）
- 针对每个具体业务场景（如“团购”）构建独立的子工作流 Agent。
- 子工作流内部整合多源信息，包括：
  - 对应业务 API 返回的实时数据（如团购库存、价格等）  
  - 用户画像中的个性化信息（如偏好、历史行为）  
  - 基于用户问题通过 RAG 检索到的商家知识或用户评论  
- 最终由 LLM 融合上述信息，生成精准、个性化的响应内容。

### 4. 行业特性的动态注入
- 架构支持多行业灵活适配。
- 在回复生成阶段，可动态注入以下领域知识：
  - 行业角色设定（如“咖啡师”、“美容顾问”）  
  - 业务目标（如促转化、提复购、增好评）  
  - 语言风格（如亲切、专业、简洁等）
- 该机制显著提升响应内容的：
  - 专业性  
  - 行业上下文贴合度  
  - 场景适应灵活性

# 意图识别与分类

在意图分类的设计中，不能仅依赖对用户 Query 的纯语义（NLP）分析来划分意图，否则往往会导致意图类别过多、结构过于复杂，不仅降低识别准确率，还会增加维护成本。更合理的做法是结合实际业务场景进行抽象与优化：仅针对那些需要调用专属业务 API 并依赖业务数据产出结果的场景进行意图识别并单独分类；对于不依赖业务数据、能够直接基于通用常识生成回复的情况，则可统一归为“其他意图”。这一策略能够有效减少不必要的分类，提升系统的可维护性与执行效率，同时提高场景路由的准确性。

## 意图识别/分类的评测：如何识别意图识别的准确性呢？
有效控制大模型输出质量的关键在于建立完备(或逐步完备)的评测集和科学的评测指标。评测集的构建应涵盖多样化的场景，以确保模型在不同情况下的表现能够得到全面评估。
在意图识别模块（即门店智能体架构中的第一次 LLM 调用）中，**准确、鲁棒且高效的意图分类**是后续子工作流正确执行的前提。因此，建立科学、可量化的评估体系至关重要。

### 一、评测集构建原则

高质量的评测依赖于**代表性强、覆盖全面、标注一致**的测试数据集：

#### 1. 场景覆盖全面
- 覆盖所有已定义的核心业务场景（如团购、订座/排队、到店礼、菜品推荐等）。
- 包含边界场景（如多意图、模糊表达、非业务相关问题）。
- 涵盖不同行业（餐饮、美容、零售等）的典型用户表达。

#### 2. 表达形式多样
- 包含口语化、简写、错别字、方言变体等真实用户输入。
- 覆盖长短句、疑问句、陈述句、祈使句等多种句式。
- 包含带上下文的多轮对话片段（用于评估上下文感知能力）。

#### 3. 标注规范统一
- 明确定义每个意图类别的边界与示例。
- 对多意图样本进行显式标注（如“团购+菜品推荐”）。
- 由多人标注并计算标注一致性（如 Cohen’s Kappa > 0.8）。

---

### 二、核心评测指标

根据任务特性，采用以下多层次指标进行综合评估。其中，**精确率（Precision）、召回率（Recall）和 F1-score** 是意图识别中最关键的基础指标，下面结合其定义与业务意义详细说明。

#### 1. 基础分类指标（适用于单意图场景）

在意图识别任务中，我们通常关注模型是否能正确判断用户输入属于某一特定意图（例如“团购”）。为此，需先理解以下四个基本统计量（以“团购”意图为正例）：

|                | **真实为团购（正例）** | **真实非团购（负例）** |
|----------------|------------------------|------------------------|
| **预测为团购** | True Positive (TP)     | False Positive (FP)    |
| **预测非团购** | False Negative (FN)    | True Negative (TN)     |

基于此，定义如下核心指标：

##### ✅ 精确率（Precision）——“宁缺毋滥”
> **在所有被模型判为‘团购’的样本中，有多少是真的团购？**

公式：
\[
\text{Precision} = \frac{TP}{TP + FP}
\]

- **高 Precision**：说明模型很“谨慎”，一旦说“是团购”，大概率没错。
- **低 Precision**：模型容易把其他意图（如“到店礼”）误当成“团购” → 导致错误路由。
- **业务意义**：避免因误判触发错误服务流程（如错误发放优惠券），影响用户体验或造成资损。

##### ✅ 召回率（Recall）——“宁可错杀，不可放过”
> **在所有真实的‘团购’请求中，模型成功找出了多少？**

公式：
\[
\text{Recall} = \frac{TP}{TP + FN}
\]

- **高 Recall**：几乎所有的团购请求都被识别出来了，漏得少。
- **低 Recall**：很多用户明明想团购，却被分到其他流程 → 用户需求被遗漏。
- **业务意义**：确保关键用户意图不被漏掉，保障服务覆盖率和转化机会。

##### ✅ F1-score —— 精确率与召回率的“平衡点”
> 因为 Precision 和 Recall 往往互相矛盾（提高一个，另一个可能下降），所以用 **F1-score** 综合衡量。

公式（调和平均）：
\[
F1 = 2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}
\]

- F1 越高，说明模型在**准确性和覆盖性之间取得了较好平衡**。
- 使用调和平均（而非算术平均）是因为它对极端值更敏感，更能反映模型整体失效风险。
- **业务意义**：作为主评估指标，反映意图识别模块的综合性能。

> 📌 **建议**：按每个意图类别分别计算 Precision、Recall 和 F1，并报告 **宏平均 F1（Macro-F1）**（各类别平等权重）和 **加权平均 F1（Weighted-F1）**（按样本量加权），以全面评估模型表现。

#### 2. 多意图处理指标（若支持多标签分类）
- **Subset Accuracy**：预测标签集合完全匹配才算正确（严格但合理）。
- **Hamming Loss**：错误标签比例，越低越好。
- **Label-wise F1**：对每个意图单独计算 F1 后平均。


---

### 三、评估流程建议

1. **离线评估（Offline Evaluation）**
   - 使用静态评测集定期评估模型版本迭代效果。
   - 结合混淆矩阵分析易混淆意图对（如“订座” vs “排队”），针对性优化提示词或分类逻辑。

2. **在线评估（Online Evaluation）**
   - 通过影子模式（Shadow Mode）部署新模型，对比线上现行模型的意图分布与后续转化指标。
   - 监控关键业务路径的意图识别准确率与用户满意度（如 NPS、会话完成率）。

3. **持续迭代机制**
   - 建立“bad case 回流”机制：将线上识别错误或用户反馈不佳的样本加入评测集。
   - 定期扩充评测集，覆盖新出现的用户表达或新增业务场景。

### 智能体提示词效果的评测
采用迭代式提示词调优的策略，具体步骤如下：
- 首先，通过“完备”的评测集进行评测；
- 然后，进行错误分析并归类错误原因；
- 接着，针对占比最大的错误制定Prompt优化策略，同时制定优化目标（即提升评测指标的预期幅度）；
- 随后，实施优化迭代；
- 在此后的错误分析中检查是否达成优化目标；
- 最后，循环迭代这一过程，直至模型性能达到业务预期目标。

由于真实项目场景的业务通常较为复杂，几乎不可能在一开始就收集到完备的评测集。因此，在产品业务技术架构中，如何快速收集到bad case的链路设计显得尤为重要。这不仅是一个不断优化模型结果的关键功能，也是监控线上运行的重要环节。
**“链路设计”指什么？**  
   - 技术上要建立一套自动化机制，例如：
     - 用户点击“回答没帮助”按钮 → 自动记录该对话上下文；
     - 后台监控低置信度预测（如意图识别概率 < 0.6）→ 标记为可疑样本；
     - 客服介入的对话自动归档为潜在 Bad Case；
     - 定期抽样人工审核，打标错误类型。

> 初始数据永远不够，必须通过**线上反馈 + 自动化采集 + 人工审核**构建一个持续进化的“Bad Case 回流管道”，这是 AI 产品落地的核心能力之一。

另外关于**“语言模型幻觉”与评估修正**，语言模型产生幻觉的主要原因在于现有的训练和评估方法会**奖励“猜测”而不是承认不确定性**。有一个简单直接的修正方法：对自信的错误惩罚要比对不确定性带来的保留惩罚更重，并且对恰当地表达不确定性的回答给予部分分数。

#### ✅ 解释：

1. **什么是“幻觉”（Hallucination）？**  
   - 指模型**自信地编造虚假信息**，比如：
     - 用户问：“你们有生日优惠吗？”  
       模型答：“有的！本月生日可享 8 折，需提前一天预约。”（但商家其实没有此活动）
     - 这不是“不知道”，而是“胡说八道还说得特别肯定”。

2. **为什么会这样？根源在训练/评估机制！**  
   - 传统训练目标（如最大似然估计）鼓励模型“给出流畅、完整的回答”。
   - 评估指标（如 BLEU、ROUGE 或人工打分）往往偏好“看起来专业、信息量大”的回答，哪怕内容是错的。
   - 结果：模型学会“宁可瞎猜也不能说不知道”，因为**猜对了得高分，猜错了可能只扣一点分，但说‘我不知道’会被认为‘没用’而得低分**。

3. **如何修正？—— 改变“打分规则”！**  
   提出一个更合理的评估原则：
   
   | 回答类型 | 示例 | 应得分数 |
   |--------|------|--------|
   | **自信且正确** | “我们支持排队，当前前面有 3 桌。”（API 确认） | ✅ 高分（满分） |
   | **自信但错误** | “我们支持排队。”（实际不支持） | ❌ **重罚**（比普通错误扣更多） |
   | **表达不确定性但合理** | “我不确定是否支持排队，建议您电话咨询门店。” | ⭕ **给部分分数**（鼓励诚实） |
   | **直接说不知道** | “我不知道。” | ⭕ 可接受（优于胡编） |

4. **为什么这样设计？**  
   - **重罚“自信的错误”**：因为这类回答最具欺骗性，最容易误导用户、损害信任。
   - **奖励“恰当的不确定性”**：让模型学会在信息不足时“保守回答”，而不是强行生成。
   - 这种评估方式更贴近**真实业务需求**：宁可少说，不要说错。

> 💡 **举个门店场景的例子**：  
> 用户问：“你们家小龙虾是活的吗？”  
> - ❌ 幻觉回答：“是的，每天现捞！”（实际是冷冻的）→ **严重错误，应重罚**  
> - ✅ 诚实回答：“抱歉，我不清楚食材来源，建议您询问店员。” → **应给予肯定**

#### ✅ 总结一句话：

> 真实世界太复杂，不能指望模型一开始全对；  
> 我们要做的，是**快速发现它错在哪**（Bad Case 回流），  
> 并教会它**宁可说‘不确定’，也不要瞎编**（修正评估机制）。

## 5. 关于多智能体架构模式

业界多智能体交互主要分为 **中心化** 和 **去中心化** 两种基本模式，也可结合为 **混合模式**。不同模式在控制逻辑、扩展性、适用场景等方面各有优劣。

### 模式对比总览

| 模式 | 核心思路 / 交互方式 | 优点 | 缺点 | 适用场景 |
|------|-------------------|------|------|----------|
| **中心化模式 (Manager/Coordinator)** | 有一个核心协调者（Manager Agent）接收任务请求，将任务拆分后分配给不同的专家 Agent，最终汇总结果返回给用户。类似总控调度。 | - 流程清晰、容易管理和监控<br>- 易于保证输出的一致性<br>- 易于维护上下文和状态 | - 中心节点可能成为性能瓶颈或单点故障<br>- 扩展性差（随着 Agent 数量增加，中心的负担加重） | - 复杂任务需要整合多方面信息<br>- 有统一结果输出的项目（如报告生成、数据汇总等）<br>- 企业内部流程自动化 |
| **去中心化模式 (Handoff)** | Agents 基本平等，通过“Handoff”机制传递任务控制权，带着上下文从一个 Agent 切换到另一个。可单向或双向移交。 | - 灵活性强，可按需设计移交流程<br>- 无单点瓶颈，具备较强的可扩展性<br>- 更接近真实业务场景下的多部门协作 | - 多轮移交可能导致上下文丢失或不一致<br>- 缺少全局统一监控，任务全貌不易追踪<br>- 结果整合需要额外机制 | - 分诊型任务（客服、技术支持、销售等）<br>- 场景独立且分离度高的服务链路<br>- 用户与某个特定角色的长时间互动 |
| **混合模式 (Hybrid)** | 在总体架构中保留一个中心协调者，但允许部分子任务在专家之间去中心化地移交。中心可控制关键节点，非关键节点可 peer-to-peer 协作。 | - 兼顾控制性与灵活性<br>- 可定制关键路径的集中管理，同时让其他部分更灵活地移交<br>- 适合任务复杂度高但部分环境动态变化的场景 | - 架构复杂度高，设计成本大<br>- 需要同时维护中心节点和去中心化环节的稳定性 | - 大型多部门业务协作系统<br>- 需要统一标准输出同时支持局部灵活交互的场景（例如：企业知识库 + 各部门定制化客服） |

### 详细说明

#### 1. 中心化模式（Manager/Coordinator）

- **核心思路**：  
  分解任务难度，设置一个中心的“大管家”（Manager Agent），负责接收用户初始请求，并像调用工具一样，通过 **tool calls** 将子任务分配给多个“专家” Agent。每个专家专注于特定领域（如团购、订座、菜品推荐等）。Manager 最终收集并整合所有结果，形成统一输出。

- **典型流程**：

- **优势**：  
  控制流清晰，便于调试、监控和保障输出一致性，特别适合需要**全局统筹**的任务。

- **局限**：  
  Manager 成为系统瓶颈，Agent 数量增多时调度开销显著上升。

---

#### 2. 去中心化模式（Handoff）

- **核心思路**：  
  不强制所有请求经过单一中心。Agent 之间通过 **Handoff（移交）机制** 动态转移对话控制权。移交时通常携带当前对话上下文，目标 Agent 接管后可直接与用户交互。

- **典型场景 — 对话分诊（Conversation Triage）**：  
  - 初始由 **Triage Agent** 接收用户问题；
  - 判断意图后，直接 **Handoff** 给销售 Agent、技术支持 Agent 或订单管理 Agent；
  - 后续交互完全由目标 Agent 主导，必要时还可 Handoff 回原 Agent 或其他专家。
<img width="740" height="368" alt="image" src="https://github.com/user-attachments/assets/4f1e66ea-baf8-437a-b2a1-c1215925d802" />


- **优势**：  
  架构轻量、扩展性强，更贴近现实业务中“部门间转接”的协作逻辑。

- **挑战**：  
  多次移交可能造成上下文碎片化，缺乏全局视图，难以追踪端到端任务状态。

---

#### 3. 混合模式（Hybrid）

- **核心思路**：  
  在整体架构中保留一个轻量级的中心协调者，用于把控关键路径（如身份验证、权限校验、结果审核），而将非核心或高度专业化的子任务交由专家 Agent 通过 Handoff 自主协作。

- **优势**：  
  既保留了中心化模式的可控性和一致性，又引入了去中心化的灵活性和可扩展性。

- **适用性**：  
  特别适合**大型、复杂、多变**的企业级智能体系统，例如：
  - 统一入口的企业客服平台；
  - 结合通用知识库与部门专属策略的智能导购系统。

- **代价**：  
  架构设计与运维复杂度显著提升，需精细划分“集中”与“分布”的边界。

### 门店智能体的多智能体模式调研
调研分析业界其他产品（飞猪、支付宝商家经验助手等），采用中心化交互模式：Planning思考规划 + 丰富的业务Tool + Agent as Tool，可以解决复杂业务问题，目前行业内也是该主流解决方案

## 6.1、商圈Query改写语料生成

### 多行业生成，重点关注行业

和业务沟通，她们认为需要重点关注的行业包括：  
**口腔、法律、少儿培训、妇产、维修、宠物医院、植发、驾校、职业培训、回收、眼科、中医、体检、综合医院、皮肤科**

**目标**：以这些行业为重点，看能否 SFT 模型泛化到其他行业，尽量避免新增行业后的继续微调训练。

### 商圈Query改写语料生成维度（业务角度）

- 搜索POI列表  
- 搜索商品/服务/团购/优惠活动列表  
- 周边搜：搜周边停车场、充电桩、景区等周边设施  

### 以口腔行业为例的语料生成思路

#### POI搜索的生成思路

采用两阶段生成策略：  
首先，模型生成 POI 搜索问题的类别，确保分类体系全面且清晰，覆盖各类潜在查询意图；  
随后，针对不同类别生成对应的最终问题，以构建结构化且多样化的语料集。  

该策略不仅保障了语料生成过程中的体系完备性，也有效提升了生成结果的相关性、丰富性和覆盖广度。

问题应该多样化，覆盖不同的服务、人群、位置、评价等。例如：

- **针对特定服务**：拔牙、洗牙、补牙、种植牙、正畸等。  
- **针对地点**：本地、某个城市、某个区域。  
- **针对评价**：口碑好、排名高、性价比高。  
- **针对特定人群**：儿童牙科、老人牙科、急诊服务。  
- **其他方面**：价格、保险、新技术等。

#### 商品搜索的生成思路

问题应该多样化，口腔行业的常见商品和服务：

- **商品**：如牙膏、牙刷、牙线、漱口水等口腔护理产品。  
- **服务**：如洗牙（洁牙）、拔牙、补牙、根管治疗、牙齿矫正（正畸）、种植牙、美白牙齿等。  
- **优惠活动**：如团购、折扣、套餐优惠、会员专享、节日促销等。

进一步细化类别，可以包括：

- **清洗类**：洗牙、超声波洁牙等。  
- **治疗类**：补牙、根管治疗、拔牙等。  
- **美容类**：牙齿美白、贴面、矫正。  
- **预防类**：儿童涂氟、窝沟封闭。  
- **商品类**：口腔护理产品。  
- **综合套餐**：体检套餐、全家套餐。  
- **优惠形式**：团购、折扣、免费检查、赠品。

### 推广到其他行业的实施路径

以口腔行业的生成思路为 **few-shot**，让 LLM 针对其他行业生成语料准备的生成思路，然后执行生成任务。
