# 门店智能体架构设计原则

基于当前 LLM 的能力边界，门店智能体场景短期内仍难以直接实现“一次性输入全量信息，并精准输出完整答案”的理想化模式。因此，在门店智能体的实际设计中，考虑到 LLM 在处理“大而全”的综合任务时，性能和效率难以兼顾，我们将复杂任务拆分为多个可独立处理的“小任务”，并采用模块化架构按步骤完成，从而提升回复质量、缩短响应延迟、降低生成成本。

## 架构核心特性

为满足智能体场景对响应时间（RT）的高要求，**每轮交互中的模型调用严格控制在两次以内**：

### 1. 第一次调用：意图识别
- 基于统一抽象的业务场景，精准识别用户意图。
- 将用户请求路由至对应的业务场景模块。
- 采用qwen-plus模型，基于prompt提示词，让大模型直接进行意图识别

### 2. 第二次调用：回复内容生成
- 在该阶段，LLM 融合多源数据生成最终响应，包括：
  - 业务 API 返回的实时信息  
  - RAG 检索到的商家知识与用户评论  
  - 用户画像等个性化数据
- 每个业务场景采用**独立子工作流**生成响应内容。
- 支持多种典型场景（如团购、订座/排队、到店礼、菜品推荐等），各场景拥有专属子工作流，确保：
  - 高可维护性  
  - 良好的扩展性  
  - 强化的场景化适配能力
 

## 核心设计原则

门店智能体架构采用 **“单 Agent 模式”**，整体方案可概括为：

> **业务场景统一抽象 + 分而治之 + 模块化子工作流 + 动态提示词**

该设计在保证模块化与多行业适配能力的同时，兼顾响应质量、交互效率与生成成本控制。

## 关键组件说明

### 1. 业务场景统一抽象
- 从行业特性及业务需求出发，对门店智能体的服务范围进行统一抽象与分类。
- 提炼出核心业务场景，例如：
  - 团购  
  - 订座 / 排队  
  - 到店礼  
  - 菜品推荐  
  - ……

### 2. 意图识别节点（第一次 LLM 调用）
- 基于上述统一抽象的业务场景分类，构建智能体的业务服务能力边界。
- 精准识别用户意图，并完成路由规划，将用户请求匹配至最合适的业务场景。

### 3. 业务场景子工作流 Agent（第二次 LLM 调用）
- 针对每个具体业务场景（如“团购”）构建独立的子工作流 Agent。
- 子工作流内部整合多源信息，包括：
  - 对应业务 API 返回的实时数据（如团购库存、价格等）  
  - 用户画像中的个性化信息（如偏好、历史行为）  
  - 基于用户问题通过 RAG 检索到的商家知识或用户评论  
- 最终由 LLM 融合上述信息，生成精准、个性化的响应内容。

### 4. 行业特性的动态注入
- 架构支持多行业灵活适配。
- 在回复生成阶段，可动态注入以下领域知识：
  - 行业角色设定（如“咖啡师”、“美容顾问”）  
  - 业务目标（如促转化、提复购、增好评）  
  - 语言风格（如亲切、专业、简洁等）
- 该机制显著提升响应内容的：
  - 专业性  
  - 行业上下文贴合度  
  - 场景适应灵活性

# 意图识别与分类

在意图分类的设计中，不能仅依赖对用户 Query 的纯语义（NLP）分析来划分意图，否则往往会导致意图类别过多、结构过于复杂，不仅降低识别准确率，还会增加维护成本。更合理的做法是结合实际业务场景进行抽象与优化：仅针对那些需要调用专属业务 API 并依赖业务数据产出结果的场景进行意图识别并单独分类；对于不依赖业务数据、能够直接基于通用常识生成回复的情况，则可统一归为“其他意图”。这一策略能够有效减少不必要的分类，提升系统的可维护性与执行效率，同时提高场景路由的准确性。

## 意图识别/分类的评测：如何识别意图识别的准确性呢？
有效控制大模型输出质量的关键在于建立完备(或逐步完备)的评测集和科学的评测指标。评测集的构建应涵盖多样化的场景，以确保模型在不同情况下的表现能够得到全面评估。
