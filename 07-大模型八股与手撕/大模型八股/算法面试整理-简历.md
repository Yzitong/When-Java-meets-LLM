## 一、针对实习经历的提问

### 美团
#### **Q1：你在美团酒旅用户增长组实习期间，设计了智能外呼评测系统。你提到“评测准确率达到90%以上”，这个指标是如何定义和验证的？如果模型在某些边缘 case 上表现不稳定，你会如何优化 prompt 或评估机制？**

#### ✅ 期望回答：
> 我们将“评测准确率”定义为：由 LLM 自动生成的评分结果与人工标注（3人交叉校验）一致的比例。我们构建了一个包含 2,000+ 条真实外呼对话的黄金测试集，覆盖正向转化、拒绝加微、模糊意向等典型场景。
>
> 对于边缘 case（例如用户说“我再想想”），我们发现初始 prompt 容易误判为“高意向”。为此，我们引入了**分层判断逻辑**：先判断是否明确拒绝，再判断是否有积极信号，最后对模糊语句默认归为“中性”。同时，在 prompt 中显式加入 few-shot 示例，展示“犹豫型”语句的正确打标方式。
>
> 此外，我们还设计了**置信度阈值机制**：当模型输出的概率分布熵较高时，自动标记为“需人工复核”，避免低置信预测影响业务决策。这套机制使模糊样本的误判率下降了 35%。

### **Q2：你在高德地图实习时实现了“门店智能体”，采用“两次模型调用”策略（意图识别 + 场景化生成）。为什么选择限制为两次调用？有没有考虑过使用多轮 Agent 协作（如 ReAct）？这种设计在面对复杂用户 query（如“附近有能做种植牙又支持医保的口腔医院吗？”）时如何保证效果？**

#### ✅ 期望回答：
> 限制两次调用的核心原因是**线上 RT（响应时间）要求极高**——高德 C 端产品要求 P95 延迟 < 1.5 秒。而多轮 ReAct 或多 Agent 协作会显著增加调用链路和不确定性延迟，不符合业务 SLA。
>
> 针对复杂 query，我们的解法是：
> 1. **在意图识别阶段保留结构化槽位信息**：不仅识别出“口腔医院”，还通过 NER 提取出“种植牙”“医保”等关键约束；
> 2. **在子工作流中融合多源数据**：API 查询支持“服务类型+医保资质”联合过滤，RAG 检索也基于这些槽位动态构造查询；
> 3. **兜底策略**：若 API 无结果，则引导用户放宽条件（如“暂无支持医保的种植牙服务，是否查看自费选项？”）。
>
> 实际上线后，复杂 query 的任务完成率（用户获得有效答案）达 88%，平均延迟 1.18 秒，验证了该架构的可行性。

## 二、针对项目经历的提问

### **Q3：你在“智道”通信教育 Agent 项目中，提到使用 GraphRAG + LoRA 微调，并设计了“领域加权损失函数”。能否详细解释这个损失函数的设计动机？为什么给“推导步骤”更高权重？这对模型训练稳定性有何影响？**

#### ✅ 期望回答：
> 在通信教育场景中，学生不仅需要答案，更关注**推导过程是否严谨**（如香农公式推导）。但通用 LLM 倾向于直接给出结论，忽略中间逻辑。
>
> 因此，我们在 self-instruct 构建的数据集中，人工标注了每个 token 是否属于“核心公式”或“关键推导步骤”，并据此设计加权交叉熵损失：
> ```python
> loss = -sum( weight_i * log(p_i) )  # weight_i ∈ [1.0, 1.5]
> ```
> 其中，关键步骤权重设为 1.2–1.5，普通描述保持 1.0。
>
> 实验发现，适度加权（≤1.5）可显著提升步骤覆盖率（62% → 91%），且训练 loss 收敛稳定；但若权重过高（如 2.0+），会导致模型过度关注局部而忽略整体流畅性，甚至出现重复生成。因此我们通过消融实验确定了最优区间。

### **Q4：你提到构建了“Agent 驱动的动态 RAG 系统”，通过 Function Call 决定是否检索。这个决策逻辑是如何实现的？是规则-based 还是模型-based？如何避免“该检不检”或“不该检乱检”？**

#### ✅ 期望回答：
> 我们采用 **混合决策机制**：
> - **第一层：规则过滤**。对明显事实型问题（含“是多少”“定义是什么”等关键词）强制触发检索；
> - **第二层：轻量模型判断**。对模糊问题，用微调后的 tiny-BERT 分类器预测“是否需要外部知识”，阈值设为 0.7；
> - **第三层：Agent 自反思**。在生成过程中，若检测到“我不确定”“可能”等不确定性表述，自动回溯触发检索。
>
> 为防止误判，我们设置了两个保障：
> 1. **负采样训练**：在训练集中加入大量“无需检索”的简单问题（如“你好”），降低 false positive；
> 2. **检索结果相关性校验**：若召回 top-3 文档与 query 的 embedding 相似度均 < 0.5，则放弃使用检索结果，转为生成兜底回答。
>
> 最终系统在测试集上达到 94.6% 的检索精准率（即触发检索时，结果确实有用）。

## 三、针对论文与科研能力的提问

### **Q5：你的论文聚焦“6G + 多智能体协同”，但实习项目多为单 Agent 架构。你如何看待多智能体在工业落地中的挑战？你认为当前哪些场景真正需要多 Agent 而非单 Agent + 工具调用？**

#### ✅ 期望回答：
> 这是个很好的问题。我在论文中探索的是**未来泛在智能网络下的协同范式**，但在当前工业界，**单 Agent + 工具调用仍是性价比最高的方案**，原因有三：
> 1. **工程复杂度**：多 Agent 需解决通信、状态同步、死锁等问题，运维成本高；
> 2. **收益边际递减**：多数业务场景（如门店问答）可通过模块化子工作流解决，无需真正“协作”；
> 3. **评估困难**：多 Agent 系统的端到端效果难以归因。
>
> 但我认为以下场景值得尝试多 Agent：
> - **跨组织协作**：如保险理赔涉及医院、交警、保险公司三方数据，需独立 Agent 代表各方；
> - **长期任务规划**：如旅行规划 Agent 需协调航班、酒店、景点多个子 Agent 动态调整行程；
> - **安全隔离需求**：金融场景中，风控 Agent 与客服 Agent 必须物理隔离。
>
> 目前我更倾向于“**混合模式**”：主流程由单 Agent 控制，仅在必要环节 Handoff 给专用 Agent，兼顾效率与灵活性。
