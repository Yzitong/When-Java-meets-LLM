# 计算机网络常考八股

## 1. HTTP 请求报文的解析过程（从 TCP 连接到报文处理）

HTTP 基于 TCP 协议传输，因此解析过程需先从 “连接建立” 开始，再到应用层的报文格式解析，最终落地到业务处理。

整体流程可分为 7 步：

**步骤 1：建立 TCP 连接**

客户端与服务器通过**TCP 三次握手**建立可靠连接：

- 客户端发送 `SYN` 包，请求建立连接；
- 服务器回复 `SYN+ACK` 包，确认请求；
- 客户端发送 `ACK` 包，连接建立完成。
  *注：HTTP/1.1 支持 “长连接”（`Connection: keep-alive`），连接可复用；HTTP/1.0 默认 “短连接”，一次请求对应一次连接。*

**步骤 2：接收 HTTP 请求报文（TCP 层重组）**

服务器的 TCP 协议栈接收客户端发送的**TCP 分段**（因 TCP 是 “面向字节流” 协议，数据会被拆分为多个分段），并按顺序重组为**完整的 HTTP 请求报文**（避免因分段乱序导致解析错误）。

![image-20250909142036498](https://raw.githubusercontent.com/Yzitong/When-Java-meets-LLM/main/images/image-20250909142036498.png)

**步骤 3：解析请求行（Request Line）—— 确定 “请求目标”**

请求行是报文的第一行，格式为 `[请求方法] [请求URI] [HTTP版本]`，解析核心是提取 3 个关键信息：

- **请求方法**：明确客户端需求（如 GET = 获取资源、POST = 提交数据、PUT = 修改资源、DELETE = 删除资源）；
- **请求 URI**：定位目标资源路径（如 `/api/user?name=test`，包含路径和查询参数）；
- **HTTP 版本**：确定协议规则（如 HTTP/1.1 支持长连接、HTTP/2 支持多路复用）。
  *示例：`GET /index.html?page=1 HTTP/1.1`*

**步骤 4：解析请求头（Request Headers）—— 获取 “请求约束与客户端信息”**

请求头紧跟请求行，格式为 `键: 值`（每行一个），解析核心是提取客户端环境和请求规则，常见字段及作用：

| 字段名           | 作用示例                                                     |
| ---------------- | ------------------------------------------------------------ |
| `Host`           | 指定服务器域名 + 端口（如 `www.baidu.com:80`），用于 “虚拟主机”（一台服务器承载多个域名） |
| `User-Agent`     | 客户端身份（如 `Chrome/120.0.0.0`），服务器据此适配页面（如移动端 / PC 端） |
| `Cookie`         | 客户端存储的会话信息（如 `SessionID=abc123`），用于身份验证  |
| `Content-Type`   | 请求体的数据格式（如 `application/json`），仅 POST/PUT 等有请求体的方法需要 |
| `Content-Length` | 请求体的字节数，服务器据此判断何时接收完请求体               |

解析时需按 “键值对” 格式逐行处理，直到遇到**空行**（`\r\n\r\n`）—— 空行是 HTTP 协议的强制分隔符，标志请求头结束。

**步骤 5：解析请求体（Request Body）—— 提取 “提交的数据”**

仅当请求方法需要提交数据时（如 POST、PUT）存在，GET/DELETE 通常无请求体，解析逻辑分两种场景：

1. **已知长度（Content-Length）**：按 `Content-Length` 字段指定的字节数读取后续数据，作为完整请求体；
2. **未知长度（Chunked 编码）**：若请求头含 `Transfer-Encoding: chunked`，则按 “分块格式” 读取（每块以 “分块大小 + 分块数据” 组成，直到遇到 `0\r\n\r\n` 表示结束），适用于上传大文件等场景。

最后，根据 `Content-Type` 解析请求体内容（如 JSON 字符串转对象、表单数据 `application/x-www-form-urlencoded` 拆分为键值对）。

**步骤 6：业务逻辑处理，构建 HTTP 响应**

报文解析完成后，服务器进入业务层处理：

- 路由匹配：根据 “请求方法 + URI” 找到对应接口（如 `/api/login` 对应登录接口）；
- 业务执行：验证参数、查询数据库、处理数据（如验证账号密码是否正确）；
- 响应构建：生成 HTTP 响应报文（含状态码、响应头、响应体，如登录成功返回`200 OK`+ 用户信息）。

**步骤 7：TCP 连接管理（收尾）**

响应报文通过已建立的 TCP 连接返回给客户端后，根据连接类型处理：

- 短连接（HTTP/1.0 默认）：服务器主动发起 “TCP 四次挥手”，关闭连接；
- 长连接（HTTP/1.1 `Connection: keep-alive`）：保持连接，等待客户端后续请求（若超时无请求，服务器会主动关闭）。

## 2. HTTP 与 HTTPS 的核心区别（从安全、性能、协议设计维度对比）

HTTPS 的本质是 “**HTTP over TLS/SSL**”（在 HTTP 和 TCP 之间增加了 TLS/SSL 安全层），核心解决 HTTP 的 “明文传输” 安全问题，具体区别如下：

| 对比维度         | HTTP (超文本传输协议)                       | HTTPS (安全超文本传输协议)                                   |
| ---------------- | ------------------------------------------- | ------------------------------------------------------------ |
| **核心安全机制** | 无加密、无身份认证、无完整性校验 → 明文传输 | 1. **加密**：对称加密（AES）传输数据，非对称加密（RSA）协商密钥； 2. **认证**：服务器需 CA 签发证书，验证身份防冒充； 3. **校验**：MAC / 哈希（SHA）确保数据未被篡改 |
| **协议层次**     | 应用层直接基于 TCP 传输                     | 应用层（HTTP）→ TLS/SSL 层（安全层）→ TCP 层                 |
| **默认端口**     | 80                                          | 443                                                          |
| **证书需求**     | 无需任何证书                                | 必须配置**可信 CA（证书颁发机构）** 签发的服务器证书（自签证书会被浏览器标记 “不安全”） |
| **传输性能**     | 快，无额外握手 / 加密开销                   | 慢，需额外 TLS 握手（1-2 次 RTT 延迟），且数据需加密 / 解密（耗 CPU） |
| **资源消耗**     | 服务器 / 客户端资源消耗低                   | 资源消耗高（服务器需优化：如 SSL 加速卡、TLS 会话复用）      |
| **地址标识**     | URL 以 `http://` 开头                       | URL 以 `https://` 开头                                       |
| **浏览器提示**   | 现代浏览器对 HTTP 页面标记 “**不安全**”     | 地址栏显示 “小锁” 图标，标记 “安全”                          |

### →补充：HTTPS 为何能防中间人攻击？

中间人攻击（如拦截客户端与服务器的通信）的核心是 “伪造身份 + 窃取数据”，而 HTTPS 通过两步防护：

1. **证书验证**：客户端会校验服务器证书的有效性（是否由信任的 CA 签发、域名是否匹配、是否过期），中间人无法伪造可信 CA 证书；
2. **密钥协商**：对称加密的密钥通过 “服务器公钥加密” 传输，只有服务器的私钥能解密，中间人即使拦截也无法获取密钥，无法解密后续数据。



## 3.OSI七层模型

OSI（Open System Interconnect）七层模型是一种将计算机网络通信协议划分为七个不同层次的标准化框架。每一层都负责不同的功能，从物理连接到应用程序的处理。这种模型有助于不同的系统之间进行通信时，更好地理解和管理网络通信的过程。
OSI定义了网络互连的七层框架（物理层、数据链路层、网络层、传输层、会话层、表示层、应用层），即ISO开放互连系统参考模型。

![image-20250910094510817](https://raw.githubusercontent.com/Yzitong/When-Java-meets-LLM/main/images/image-20250910094510817.png)

**应用层（Application Layer）**：这是网络体系结构中的最顶层，提供用户接口和应用程序之间的通信服务。在这一层，用户可以访问各种网络应用程序，如电子邮件、文件传输和远程登录。
**表示层（Presentation Layer）**：该层负责数据的格式化、加密和压缩，以确保数据在不同系统之间的交换是有效的和安全的。它还提供了数据格式转换和语法转换的功能。
**会话层（Session Layer）**：会话层管理应用程序之间的通信会话，负责建立、维护和终止会话。它还提供了数据的同步和检查点恢复功能，以确保通信的完整性和持续性。
**传输层（Transport Layer）**：传输层为应用程序提供端到端的数据传输服务，负责数据的分段、传输控制、错误恢复和流量控制。它主要使用 TCP（传输控制协议）和 UDP（用户数据报协议）来实现这些功能。
**网络层（Network Layer）**：网络层负责数据包的路由和转发，以及网络中的寻址和拥塞控制。它选择最佳的路径来传输数据包，以确保它们能够从源主机到目标主机进行传输。
**数据链路层（Data Link Layer）**：数据链路层提供点对点的数据传输服务，负责将原始比特流转换为数据帧，并检测和纠正传输中出现的错误。它还控制访问物理媒介的方式，以及数据帧的传输和接收。
**物理层（Physical Layer）**：物理层在物理媒介上传输原始比特流，定义了连接主机的硬件设备和传输媒介的规范。它确保比特流能够在网络中准确地传输，例如通过以太网、光纤和无线电波等媒介。

## 4.TCP/IP四层模型

TCP/IP 四层模型是目前被广泛采用的一种模型，由以下 4 层组成：应用层、传输层、网络层、网络接口层

**应用层（Application Layer）**：类似于 OSI 模型中的应用层，负责处理用户与网络应用程序之间的通信。它包括诸如 HTTP、FTP、SMTP 等协议，用于实现不同类型的网络服务和应用。
**传输层（Transport Layer）**：与 OSI 模型中的传输层相对应，提供端到端的数据传输服务。在 TCP/IP 模型中，主要有两个协议：TCP（传输控制协议）和 UDP（用户数据报协议），用于确保可靠的数据传输和简单的数据传输。
**网络层（Internet Layer）**：相当于 OSI 模型中的网络层，负责数据包的路由和转发。它使用 IP（Internet Protocol）协议来定义数据包的传输路径，并处理不同网络之间的通信。
**网络接口层（Link Layer）**：与 OSI 模型中的数据链路层和物理层相对应，负责管理网络硬件设备和物理媒介之间的通信。它包括以太网、Wi-Fi、蓝牙等各种物理层和数据链路层协议。

## 5.负载均衡

在单体系统中，所有用户请求都由一台服务器处理，但随着业务增长（如用户量从 1 万到 100 万），单台服务器的 CPU、内存、带宽会成为瓶颈 —— 轻则响应变慢，重则直接宕机（“单点故障”）。

负载均衡（Load Balancing，简称 LB）正是为解决这一问题而生：**它作为分布式系统的 “流量入口”，将海量的网络请求、计算任务或数据负载，公平、高效地分配到多台后端服务器（或节点）上，避免单点过载，同时保证系统整体的稳定运行**。

![image-20250910103703760](https://raw.githubusercontent.com/Yzitong/When-Java-meets-LLM/main/images/image-20250910103703760.png)

**负载均衡的策略**

| 算法名称                             | 核心逻辑                                                     | 优势                                              | 适用场景                                                     |
| ------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------- | ------------------------------------------------------------ |
| **轮询（Round Robin）**              | 按顺序依次将请求分配给每个后端节点（如 1→2→3→1→2→3...）      | 实现简单、公平                                    | 后端节点配置相同（如所有服务器 CPU / 内存一致），无明显性能差异 |
| **加权轮询（Weighted Round Robin）** | 给性能强的节点分配更高 “权重”，权重越高接收的请求越多（如节点 1 权重 3、节点 2 权重 1，分配比例 3:1） | 能适配节点性能差异                                | 后端节点配置不同（如部分服务器是 8 核 16G，部分是 4 核 8G）  |
| **最小连接数（Least Connections）**  | 实时统计后端节点的活跃连接数，将请求分配给连接数最少的节点   | 动态适配负载，避免节点过载                        | 请求处理时间差异大（如部分请求耗时 100ms，部分耗时 10s）     |
| **IP 哈希（IP Hash）**               | 对客户端 IP 地址进行哈希计算，将同一 IP 的请求固定分配给同一节点 | 实现 “会话保持”（同一用户的请求始终到同一服务器） | 需要维持用户会话的场景（如未使用分布式 Session 的 Web 系统） |
| **URL 哈希（URL Hash）**             | 对请求的 URL 进行哈希计算，将同一 URL 的请求分配给同一节点   | 便于缓存（同一资源请求到同一节点，可复用缓存）    | 静态资源服务（如图片、CSS、JS，需利用节点本地缓存）          |

**负载均衡的好处**

1. **避免单点故障，提高系统可用性**
2. **分担负载压力，提升系统性能**：负载均衡能将海量请求 “分摊” 到多台服务器，避免单台服务器因 CPU、内存、带宽过载导致响应变慢。
3.  **提供安全防护，隐藏后端架构**：负载均衡器可作为系统的 “统一入口”，隐藏后端服务器的真实 IP 地址，避免后端节点直接暴露在公网中，减少被攻击的风险。
4. **优化资源利用率，降低成本**：没有负载均衡时，容易出现 “部分服务器过载（CPU 100%），部分服务器空闲（CPU 10%）” 的资源浪费情况。
