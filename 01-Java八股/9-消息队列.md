# 消息队列

## 1. kafka如何保证不丢失消息？

kafka是由producer、consumer、broker组成的

producer：可能会出现网络问题   解决方案：1.kafka默认是异步发送消息，可以将异步转为同步   2.增加异步回调函数来监听消息发送的结果。如果发送失败，可以在回调函数中重试   3.retries重试机制，自动发起重试

broker：缓存代理，Kafka集群中的一台或多台服务器统称broker。broker需要确保producer传来的消息是不会丢失的  kafka为了性能采用的是异步批量刷盘的实现机制(达到一定数量消息后进行存储)，如果刷盘之前系统崩溃了会面临数据丢失的问题   解决方案：1.partition副本机制和ACKs机制。每一个partition包含一个leader和多个follower，leader专门处理事务类型的请求，follower负责同步leader数据，acks参数：acks等于0（producer发完消息不等broker）存在消息丢失，acks等于1（broker拿到消息后不等follower同步）也会存在数据丢失，acks等于-1（broker拿到消息后等待follower同步）保证了数据的可靠性

consumer：可以调整offset保证消息消费完成

## 2. 限流策略有哪些？

**漏桶算法：**漏桶算法中的漏桶是一个形象的比喻，这里可以用生产者消费者模式进行说明，请求是一个生产者，每一个请求都如一滴水，请求到来后放到一个队列（漏桶）中，而桶底有一个孔，不断的漏出水滴，就如消费者不断的在消费队列中的内容，消费的速率（漏出的速度）等于限流阈值。即假如 QPS  为 2，则每 `1s / 2= 500ms` 消费一次。漏桶的桶有大小，就如队列的容量，当请求堆积超过指定容量时，会触发拒绝策略。

**令牌桶算法：**令牌桶算法同样是实现限流是一种常见的思路，最为常用的 Google 的 Java 开发工具包 Guava 中的限流工具类 RateLimiter 就是令牌桶的一个实现。令牌桶的实现思路类似于生产者和消费之间的关系。

系统服务作为生产者，按照指定频率向桶（容器）中添加令牌，如 QPS 为 2，每 500ms 向桶中添加一个令牌，如果桶中令牌数量达到阈值，则不再添加。

请求执行作为消费者，每个请求都需要去桶中拿取一个令牌，取到令牌则继续执行；如果桶中无令牌可取，就触发拒绝策略，可以是超时等待，也可以是直接拒绝本次请求，由此达到限流目的。

固定窗口算法：**固定窗口算法**又叫**计数器算法**，是一种**简单**方便的限流算法。主要通过一个支持**原子操作**的计数器来累计 1 秒内的请求次数，当 1 秒内计数达到限流阈值时触发拒绝策略。每过 1 秒，计数器重置为 0 开始重新计数。存在问题：固定判断，因此可能一次时间内出现超过QPS数。下图QPS为2，但是中间一秒可以被请求4次。

滑动日志算法：滑动日志算法是实现限流的另一种方法，这种方法比较简单。基本逻辑就是记录下所有的请求时间点，新请求到来时先判断最近指定时间范围内的请求数量是否超过指定阈值，由此来确定是否达到限流，这种方式没有了时间窗口突变的问题，限流比较准确，但是因为要记录下每次请求的时间点，所以**占用的内存较多**。
